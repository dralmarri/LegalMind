## 2. Deterministic Legal Scope Backbone — التصميم الكامل

### المدخلات
- `request_type` (من `_DraftIn`، حتمي بنيويًا).
- نص الوقائع المطبَّع (`_draft_norm_ar`، حتمي).
- الإحالات الصريحة المستخرَجة فعليًا (`_LAWREF_RE`/`_ARTNUM_RE`/`_LAW_ALIASES_TBL` — قائمة).
- الكيانات القانونية المكتشَفة (أسماء قوانين/أرقامها، أسماء مؤسسات كـ"الجمعية العامة"،
  "المدير"، إلخ — عبر مطابقة معجم ثابت، لا LLM).
- الوضع الإجرائي (procedural posture) — مثال: "منع من السفر"، "أمر أداء"، "استئناف" — يُستخرَج
  من نفس معجم `_GATES` الموسَّع (خرائط كلمات مفتاحية ثابتة، لا نموذج).
- جداول معرفة قانونية منسَّقة (منظَّمة، مراجَعة يدويًا، مؤرَّخة، مُتحقَّق منها عبر MCP قبل أي
  إضافة — **موجودة جزئيًا فعلًا**: `_GATES`، `_XREF`، `_LAW_ALIASES_TBL`، فهرس الفصول
  `_draft_chap_index`. **جدول جديد واحد مطلوب**: Legal Dependency Rule Table (§3).

### المعالجة (حتمية 100%، صفر نداء LLM)
1. تطبيع النص (قائم).
2. استخراج الإحالات الصريحة (قائم — `_draft_direct_ids`/`_draft_doc_refs`) → تُصنَّف A1 فورًا.
3. مطابقة معجم الوضع الإجرائي والكيانات → لكل مطابقة، تحديد "بُعد قانوني مطلوب" (Legal
   Dimension، §7) وربطه بجدول الاستلزام أو ببوابة الفصل القائمة.
4. مطابقة Legal Dependency Rule Table (§3) → إن وُجدت قاعدة، تُنتج مرشحًا حاكمًا A3 مباشرة.
5. مطابقة بوابات الفصول القائمة (`_draft_chap_ids`) → تُنتج نطاقًا (فصلًا) لا مرساة فردية
   (هذا فرق جوهري عن الحالي: الفصل الحاكم **نطاق بحث موسَّع**، لا **مرساة تلقائية** — القرار
   بشأن أي مادة داخله تصبح مرساة يعود لـ§3/§4، لا لعضوية الفصل وحدها).
6. توسعة XREF/الشقيقة/prin-xref لأي عنصر A1-A3 مؤكَّد (قائم، يبقى كما هو).

### المخرجات
```
DeterministicScope {
  dimensions: [
    { dimension_id, label, required: bool, source_rule_id, confidence: enum(explicit|rule|chapter_gate|keyword) }
  ],
  anchors_a1: [ {authority_id, source: "explicit_citation"} ],
  anchors_a3: [ {authority_id, dimension_id, rule_id} ],
  chapter_scopes: [ {chapter_id, dimension_id} ],   # نطاق بحث لا مرساة
}
```

### الترتيب الحتمي
كل الخطوات أعلاه تعتمد فقط على النص المطبَّع ومعاجم/جداول ثابتة — **نفس السؤال حرفيًا ينتج
نفس `DeterministicScope` حرفيًا في كل تشغيل**، بلا استثناء (لا استدعاء عشوائي، لا ترتيب اعتمادًا
على استجابة شبكة). هذا هو الضمان الذي أثبتت تجربة Frozen Axes أنه المتغيّر الحاسم غيابه.

### النسَب (Provenance)، الثقة، وسلوك الفشل
- كل عنصر مُخرَج يحمل `source_rule_id` صريحًا (لا "دلالة عامة") — تتبُّع كامل لأي قرار.
- الثقة تُشتق من نوع القاعدة (استشهاد صريح > قاعدة استلزام منسَّقة > بوابة فصل > معجم كلمات) —
  ترتيب تصنيفي (enum) لا رقم مطلق الآن (per طلب المالك: لا أوزان رقمية نهائية بعد).
- **سلوك الفشل:** إن لم يُطابق شيء إطلاقًا، `DeterministicScope` يعود **فارغًا** — لا يُبنى
  هذا كحكم "لا توجد مسائل قانونية"؛ الاعتماد الكامل ينتقل لقناة Haiku التكميلية + الاسترجاع
  الدلالي كما هو الحال اليوم. **الـBackbone الفارغ ليس فشلًا يوقف الخط — إنه حالة معلومة تُسجَّل.**

### دمج توسعات Haiku دون استبدال النطاق الحتمي
- أي مرشح يكتشفه Haiku (عبر dense/bundle/lexical كالمعتاد) يُصنَّف **C أو D فقط** ابتداءً
  (Expanded/General Scope Candidate) — **لا يمكن أن يصبح A تلقائيًا** بمجرد درجة عالية.
- إن اكتشف Haiku **نفس** المعرِّف الذي أنتجه الـBackbone كـA1/A3 مسبقًا، يُدمَج (نفس الكائن،
  لا تكرار) وتبقى رتبته A — لا يُخفَّض ولا يُرفَع بدرجة Haiku.
- إن اكتشف Haiku مرشحًا **جديدًا تمامًا** ذا صلة ببُعد قانوني **يعرفه الـBackbone كمطلوب لكن
  غير مغطى بعد** (Coverage Checker يعلمه "غير مغطى")، **لا يُرقَّى لمرساة أبدًا** — يُوسَم
  **U — Unverified Coverage Candidate** (§4-مكرر، مُعدَّل 2026-09-14) ويبقى ضمن المنافسة
  العادية فقط، مع تفعيل مسار الإصلاح/المراجعة الموصوف هناك.

## 3. Legal Dependency Layer MVP — سد فجوات نمط m30 دون Hardcoding للسؤال

### التجريد المطلوب
```
fact_pattern / legal_problem  →  latent_legal_mechanism  →  governing_authority
```
مثال `m30`: *"شريك يواجه امتناع المدير عن الدعوة وتعطيل باقي الشركاء للنصاب"* (fact_pattern) →
*"آلية اتفاق المساهمين وتحييد الحصص من التصويت عبر أمر على عريضة"* (latent mechanism، **غير
مذكور لفظًا في السؤال إطلاقًا** — هذه بالضبط الفجوة) → `legis-1-2016-m30` (governing authority).

### كيف تُبنى العلاقة بصورة قابلة للتوسع والمراجعة (لا Hardcoding لسؤال أو معرف Gold Set)
1. **مصدر القواعد الأولي:** مراجعة يدوية من محامٍ/خبير قانوني (المالك) لأنماط مسائل متكررة
   في الممارسة — **ليس** استخراجًا من سؤال Gold Set بعينه. الوحدة المُدخَلة هي **النمط
   القانوني** ("امتناع عن دعوة جمعية + تعطيل نصاب" كمفهوم عام)، لا نص سؤال `gs-0036` حرفيًا.
2. **بنية القاعدة** (جدول جديد، يماثل بنية `_GATES` لكن أدق تحبيبًا):
   ```
   LegalDependencyRule {
     rule_id, label (اسم الآلية بالعربية),
     trigger_concepts: [كلمات/مفاهيم مفتاحية طبيعية — لا نص سؤال حرفي],
     trigger_logic: "ALL" | "ANY" | عدد أدنى من trigger_concepts,
     governing_authority_ids: [معرف واحد أو مجموعة ضيقة — لا فصل كامل],
     added_by, added_date, verification_note (يُستشهَد بنص المادة المؤكَّد عبر MCP),
     regression_tested: bool
   }
   ```
3. **بوابة اعتماد كل قاعدة جديدة (إلزامية، بلا استثناء، مُشدَّدة 2026-09-14):**
   نجاح القاعدة على **حالة الانحدار الأصلية وحدها لا يُحسَب دليل تعميم** — قاعدة صُمِّمت بعد
   معرفة الفشل (مثال: `m30`/`gs-0036`) قد "تنجح" عليها فقط لأنها كُتبت خصيصًا لها. **أربع فئات
   اختبار إلزامية لكل قاعدة جديدة، لا فئة واحدة:**
   - **A. صياغات موازية إيجابية غير مرئية (Positive Unseen Paraphrases):** إعادة صياغة الوضع
     الوقائعي نفسه بكلمات مختلفة تمامًا عمّا استُعمل في تأليف القاعدة — يجب أن تُطلَق القاعدة.
   - **B. سلبيات صعبة (Hard Negatives):** سيناريوهات تبدو مشابهة سطحيًا لكنها مختلفة قانونًا
     فعلًا — يجب **ألا** تُطلَق القاعدة.
   - **C. مسائل قانونية مجاورة (Neighboring Legal Issues):** مسائل من نفس المجال القانوني لكن
     آلية مختلفة — يجب **ألا** تُطلَق القاعدة (تمييز عن B: هذه قريبة موضوعيًا لا لفظيًا فقط).
   - **D. حالة الانحدار الأصلية:** التي كشفت الفجوة ابتداءً — تبقى ضرورية لكنها **الأضعف
     دليلًا لا الأقوى**، تؤكِّد عدم كسر ما دفع لبناء القاعدة، لا أكثر.
   - **مقاييس تُسجَّل لكل قاعدة (لا حكم ثنائي نجح/فشل فقط):** `precision` (نسبة الإطلاقات
     الصحيحة من كل الإطلاقات)، `trigger_rate` (تكرار الإطلاق على عينة واسعة)، `false_activation_
     rate` (من فئتي B/C تحديدًا)، `authority_survival` (هل السلطة المُنتَجة نجت فعليًا للسياق
     النهائي، لا فقط أُطلقت القاعدة).
   - تحقُّق MCP مباشر أن نص المادة المستهدَفة يعالج فعليًا الآلية الموصوفة (لا افتراض) — يبقى
     كما هو.
   - بطارية انحدار على أسئلة **محايدة** لا علاقة لها بالنمط (يمنع الانفلات — نفس درس بوابة
     `م8` القائم) + بطارية Gold Set (15/13 القائمة + التوسعة) بلا انحراف — تبقيان كما هما.
   - **قيد إلزامي على `trigger_concepts` نفسها:** تُؤلَّف بصياغة قانونية عامة مستقلة تمامًا،
     **يُحظَر نسخ نص سؤال Gold Set أو استعمال معرِّف حالته حرفيًا أو ضمنيًا** داخل منطق القاعدة
     الإنتاجي — Gold Set مرجع تقييم خارجي فقط، لا مُدخَل تصميم.
4. **مصدر توسعة مستقبلي (اقتراح لا التزام الآن):** تعدين شبه-آلي من علاقات `_prin_xref`
   القائمة (مبدأ يستشهد بمادة تشريعية) لتوليد **مرشحات** قواعد يراجعها المالك يدويًا قبل
   القبول — لا بناء تلقائي كامل، ولا "Graph" شامل الآن (كما طُلب صراحة).

### درس مطبَّق مباشرة من القسم S
تجربة Frozen Axes أثبتت أن Haiku **لا يمكن الاعتماد عليه** لاكتشاف هذه الفئة تحديدًا (m30 ظل
0/5 حتى تحت تجميد محاور أفضل الصياغات المتاحة) — هذا يبرر بيانيًا لماذا هذه الفئة **تحتاج
حصرًا** طبقة حتمية منسَّقة، لا أي تحسين لعشوائية النموذج.

## 4. تصنيف الأدلة (Evidence Classification) — الشروط الدقيقة للترقية إلى Anchor
**(مُعدَّل 2026-09-14 — حُذفت A4 من فئة Anchor بأمر صريح؛ استُبدلت بفئة مستقلة `U`)**

**المبدأ الحاسم (مباشرة من درس `m167`):** لا تصنيف بناءً على اسم القناة (`_source`) وحده. عضوية
`bundle` **شرط ضروري غير كافٍ**. الشروط الثلاثة الحصرية للترقية لفئة **A — Governing/Required
Anchor** (لا رابع، ولا مسار احتياطي/اجتهادي إطلاقًا):

| المسار | الشرط الدقيق | مثال |
|---|---|---|
| **A1 — استشهاد صريح** | المستخدم أو المستند المرفَق ذكر رقم القانون والمادة صراحة | "المادة 166 مرافعات" في السؤال |
| **A2 — إحالة تشريعية صريحة من مرساة قائمة** | مادة **مرساة بالفعل** (أي A1/A3 مؤكَّدة) تحيل **صراحة بنصها** لمادة أخرى محدَّدة (`_XREF` القائم) — عمق واحد فقط، لا تعديًا متسلسلًا | مادة مرساة تذكر "وفقًا للمادة (8) من هذا القانون" |
| **A3 — قاعدة استلزام قانوني ضيقة** (§3) | قاعدة منسَّقة ومُتحقَّقة تربط **مسألة محدَّدة** (لا فرعًا كاملًا) بمادة/مجموعة ضيقة محدَّدة سلفًا | "أمر أداء" ← م166/167 تحديدًا، لا "الباب كله" |

**ما لا يُرقَّى أبدًا لـAnchor، بلا استثناء:** عضوية `bundle`/`chapter` وحدها (مهما علت الدرجة)،
ولا درجة `dense` عالية وحدها مهما بلغت (هذا بالضبط ما رفع `m167` صدفة سابقًا)، **ولا كون البُعد
القانوني "مطلوبًا وغير مغطى"** — نقص التغطية ليس مبرِّرًا لترقية أي مرشح، هذا بالضبط ما كانت
تسمح به A4 المحذوفة.

**الفئات المتبقية — ثلاث تنافسية + فئة إشارة مستقلة (لا تدخل الحجز):**
- **B — Direct Supporting Authority:** مرشح دلالي/معجمي عالي الصلة **مرتبط ببُعد قانوني محدَّد
  في `DeterministicScope`** لكنه لا يبلغ شروط A.
- **C — Expanded Scope Candidate:** اكتشاف Haiku (محور جديد) غير مرتبط بأي بُعد محدَّد سلفًا —
  توسعة استكشافية مشروعة.
- **D — General Semantic Candidate:** كل ما تبقى في `hits` — أول ما يُقصّ تحت ضغط الميزانية.

### 4-مكرر. `U` — Unverified Coverage Candidate (تُستبدل بها A4 بالكامل)

يُوسَم بها أي مرشح ينطبق عليه: بُعد قانوني `required=true` في `DeterministicScope`، **ولا يوجد
له أي مرشح A أو B في السياق النهائي حتى الآن**، وهذا المرشح هو الأفضل دلاليًا المتاح لنفس البُعد
تحديدًا. **صلاحياتها الحصرية (لا خامسة):**
1. **تُطلِق طلب إصلاح مستهدَف** (`CoverageRepairRequest`, §7) — إشارة تشغيلية فقط.
2. **تدخل قائمة استرجاع/مراجعة إضافية** إن وُجدت (بحث موسَّع لاحق تحديدًا لهذا البُعد).
3. **تدخل طابور مراجعة بشرية/لاحقة** (Legal Dependency Layer الترشيحات المستقبلية، §3 بند 4).
4. **تُسجَّل بالكامل في التليمتري** (تكرارها عبر طلبات مختلفة مؤشر مباشر على حاجة قاعدة A3
   جديدة).

**ما لا يجوز لـ`U` إطلاقًا:**
- **لا** تدخل حجز Anchor (§6) — تتنافس فقط كفئة D عادية على الميزانية العامة إن أُريد عرضها
  في السياق أصلًا (وهذا اختياري، لا إلزامي).
- **لا** تجعل البُعد `authority_sufficient` (§7-مكرر).
- **لا** تسمح بـ`coverage_complete = true` للطلب الذي ظهرت فيه.
- **لا** تُعرَض للنموذج بصفة "مؤكَّدة" أو "حاكمة" — إن دخلت السياق أصلًا (كفئة D)، تُوسَم صراحة
  في التجميع بأنها "غير مؤكَّدة الحكم القانوني" ليعكسها التوليد بصدق إن استُشهد بها.

**مستقبل `U` (غير مُعتمَد الآن):** يمكن إعادة النظر لاحقًا في ترقية `U` لمسار A محكوم بشروط
أشد صرامة (تحقُّق بشري + قياس ضوابط سلبية §10 مقبول) — **ليست جزءًا من هذا التصميم P2**، تُذكَر
فقط كاحتمال مستقبلي صريح لا التزام.

**ضمانات صريحة ضد حماية مئات مواد الفصل:** A3 يُشترَط أن يُنتج **معرِّفًا محدَّدًا أو مجموعة
ضيقة معدودة سلفًا في القاعدة نفسها** — لا "كل مواد الفصل X" أبدًا (القاعدة القائمة `_GATES`
تبقى كما هي لإنتاج **نطاق بحث** `chapter_scope`، لا مراسٍ تلقائية — تمييز صريح جديد بين
الاثنين، §2 خطوة 5).

## 5. منطق قرار قبول الأدلة (Evidence Admission Policy)

**المشكلة المستهدَفة تحديدًا:** `نفس المادة + bundle فقط → درجة منخفضة → تُسقَط` مقابل
`نفس المادة + bundle + إصابة dense محظوظة → درجة عالية → تنجو` — منطق "الأعلى يفوز" الحالي
(`if oid not in best or sc > best[oid][1]`) يُنتج هذا التذبذب غير المقبول قانونيًا.

**التصميم: منطق قرار متعدد الأبعاد، لا درجة مُدمَجة واحدة.** كل بُعد يُفحَص ككيان منفصل قابل
للاختبار المستقل (لا وزن رقمي نهائي بعد، بأمر صريح):

```
AdmissionDecision(candidate):
    # البُعد 1: التصنيف (§4) — يُحسَم أولًا وحاكمًا
    if candidate.tier == ANCHOR (A1-A3):        # لا A4 — حُذفت، انظر §4-مكرر
        # البُعد 6: الانطباق الزمني — يُفحَص حتى للمرساة، لا استثناء
        if candidate.temporal_status == SUPERSEDED and not question.is_historical:
            return REDIRECT_TO_REPLACEMENT  # يُستبدَل بنسخته النافذة إن وُجدت، لا يُسقَط صامتًا
        # البُعد 7: التكرار — مرساتان لنفس البُعد بنفس البصمة؟ يبقى الأعلى تصنيفًا (A1>A2>A3)
        if candidate.is_duplicate_of(existing_anchor_same_dimension):
            return MERGE_KEEP_HIGHER_TIER
        return ADMIT_RESERVED  # يدخل حجز §6 — الدرجة الخام غير ذات صلة إطلاقًا هنا
                                # **لا يُفعَّل هذا المسار وحده أبدًا — انظر §6-مكرر: القبول
                                # والحجز وحدة سلوكية واحدة تُفعَّل معًا فقط بعد Shadow Mode**
    elif candidate.tier == "U":                  # Unverified Coverage Candidate، §4-مكرر
        return FLAG_FOR_REPAIR_AND_COMPETE_AS_D   # صلاحياته إشارة/إصلاح فقط، لا حجز، لا Anchor
    else:
        # B/C/D: تنافس عادي على الميزانية، لكن بترتيب يراعي أبعادًا لا الدرجة الخام فقط:
        # البُعد 4: مساهمة تغطية البُعد — هل هذا المرشح يملأ بُعدًا لم يُغطَّ بعد؟
        coverage_gain = 1 if candidate.dimension_id in unfilled_dimensions else 0
        # البُعد 1(2): قوة النسَب — B أعلى أولوية من C من D عند تعادل قوة أخرى
        # البُعد 2: الصلة الدلالية (درجة المرتِّب القائمة) — عامل ترتيب لا وحيد
        # البُعد 7: التكرار — يُستبعَد عبر بصمة P0-4 القائمة كما هي
        rank_key = (-coverage_gain, tier_order(candidate.tier), -candidate.reranker_score)
        return COMPETE_ON_BUDGET(rank_key)
```

**الأبعاد المفصولة صراحة (كما طُلب) وكيف تُستعمَل، لا كأرقام بل كشروط/ترتيب تصنيفي:**
1. الصلة الدلالية (score) — عامل ترتيب **ضمن** فئة B/C/D فقط، لا يقرر عضوية A إطلاقًا.
2. صلة السلطة القانونية (tier من §4) — الحاكم الأول في كل قرار.
3. قوة النسَب (channel/rule الذي أنتج المرشح) — يُستعمَل لفض تعارض التكرار (§7 أدناه).
4. مساهمة تغطية المسألة (coverage_gain) — يُرجَّح به الترتيب **ضمن** B/C/D فقط.
5. العلاقة الصريحة/الاستلزامية (A1-A3 tier نفسها) — مطابقة للبُعد 2 عمليًا، مُدرَجة للتوضيح.
6. الانطباق الزمني — بوابة **قبل** أي قبول، حتى للمرساة (§11 يفصّل الآلية).
7. التكرار — بصمة P0-4 القائمة، تُطبَّق على A وB/C/D معًا؛ عند تعادل البصمة، الأعلى تصنيفًا
   يبقى (لا الأعلى درجة).

هذا **يحل مشكلة `m167` مباشرة**: إن أُضيفت قاعدة A3 ضيقة لـ"أمر أداء" تشمل م166/167 تحديدًا
(وهذا الترشيح الأول المقترَح لتوسعة §3)، يصبح قبولها **مستقلًا تمامًا** عن أي إصابة `dense`
محظوظة — تُقبَل دومًا عبر `ADMIT_RESERVED`، لا عبر منافسة الدرجة.

## 6. Bounded Anchor Reservation — التصميم

**لا رفع لـ`LBL_BUDGET` القائمة.** حجز **منفصل ومحدود** يُقتطَع مسبقًا (لا يُضاف فوقها):

```
ANCHOR_RESERVATION = {
    "تشريع": {"max_chars": <صغير، يُقاس تجريبيًا لاحقًا>, "max_count": 6},
    "مبدأ قضائي": {"max_chars": <...>, "max_count": 4},
}
```

**الضمانات الإلزامية (كلها، بلا استثناء):**
- **حد أقصى مراسٍ لكل بُعد قانوني** (مثال: 3) — يمنع بُعدًا واحدًا من احتكار الحجز.
- **حد أقصى مراسٍ لكل قانون/مصدر** (مثال: 5) — يمنع قانونًا واحدًا من الهيمنة.
- **جمع تكرار قانوني (canonical dedup)** — بصمة P0-4 القائمة نفسها، تُطبَّق هنا أيضًا.
- **حظر صريح لحماية bundle كاملة** — لا مرساة إلا بشروط §4 الفردية، أيًّا كانت القناة.
- **حظر صريح لحماية فصل كامل** — نفس المبدأ، الفصل نطاق بحث لا حزمة مراسٍ.
- **تصفية زمنية** — مادة ملغاة لا تشغل خانة حجز إلا إذا كان السؤال تاريخيًا صراحة (§11).
- **تبرير إلزامي لكل مرساة** — حقل `anchor_reason = {rule_id, tier, dimension, why}` **بلا
  استثناء واحد** — أي مرساة بلا هذا الحقل تُرفَض بنيويًا (فحص آلي، لا انضباط يدوي).
- **تسجيل الفائض (overflow logging)** — إن تجاوز عدد المرشحين المؤهَّلين لـAnchor سقف الحجز،
  يُسجَّل مَن هُبِط لفئة B التنافسية بدل إسقاطه صامتًا، مع السبب.

**الهدف الصريح: حماية السلطة الحاكمة، لا إغراق السياق** — الحجز صغير عمدًا؛ توسيعه يحتاج
قياسًا يثبت الحاجة، لا افتراضًا مسبقًا.

## 7. Coverage Checker — المخطط والآلة الحالة (State Machine)
**(مُعدَّل 2026-09-14 — فصل صريح بين اكتمال البحث وكفاية السند، وB لم يعد يبلغ ANCHORED)**

**الوحدة الأساسية: البُعد القانوني المطلوب (Legal Issue / Required Legal Dimension)، لا معرِّف
الكائن.**

### المخطط (Schema) — موسَّع بحقول منفصلة صراحة

```
LegalIssue {
  issue_id, label (مثال: "أمر أداء"),
  dimensions: [
    {
      dimension_id, name (مثال: substantive_entitlement | procedural_prerequisite |
                           notice_demand_requirement | deadline | jurisdiction |
                           exception | remedy_challenge_route),
      required: bool,                          # من الـBackbone، حتمي
      requires_governing: bool,                 # من تعريف نوع القاعدة/البُعد نفسه وقت
                                                 # تأليفه (§3)، لا لكل سؤال — افتراضيًا true
      # --- الحقول المفصولة صراحة (بدل حقل survived_admission/state وحيد سابقًا) ---
      retrieval_complete: bool,                 # هل انتهى البحث فعليًا (بصرف النظر عن النتيجة)؟
      governing_authority_found: bool,          # مرشح A واحد على الأقل دخل hits؟
      governing_authority_admitted: bool,       # ونجا فعليًا للسياق النهائي؟
      supporting_authority_found: bool,         # مرشح B واحد على الأقل دخل hits؟
      supporting_authority_admitted: bool,
      authority_sufficient: bool,               # مُشتَقّ — انظر التعريف الصريح أدناه، لا تخمين
      temporal_resolved: bool,                  # هل الحالة الزمنية معروفة (نافذ/ملغى) لا "غير معروف"؟
      unverified_candidate_flagged: bool,       # هل وُسِم مرشح U لهذا البُعد؟ (إشارة لا حل)
      confidence: enum(high|medium|low),
      state: enum(UNKNOWN|SCOPED|CANDIDATE_FOUND|GOVERNING_VERIFIED|SUPPORTING_FOUND|
                  ADMITTED_GOVERNING|ADMITTED_SUPPORTING|DEAD_END)
    }, ...
  ]
}
```

### تعريف صريح لـ`authority_sufficient` (بلا استخدام أي معرِّف Gold Set)
بُعد يُعتبَر `authority_sufficient = true` **حصرًا** إذا تحقَّق أحد الشرطين التاليين، المُحدَّدين
مسبقًا وقت تأليف نوع البُعد/القاعدة (§3) لا لكل سؤال على حدة:
1. `governing_authority_admitted = true` — **يكفي وحده دومًا**، بصرف النظر عن وجود Supporting.
2. `requires_governing = false` **وجوبًا محدَّدة كذلك مسبقًا في تعريف البُعد نفسه** (بعض
   الأبعاد فعلًا لا تحتاج نصًا حاكمًا صريحًا بطبيعتها القانونية — مثال: بُعد "خلفية إجرائية
   عامة" لا "شرط جوهري") **و** `supporting_authority_admitted = true`.

**الافتراضي عند غياب تصريح `requires_governing` = `true`** — أي بُعد جديد يُضاف لا يُعتبَر
"يكفيه سند مساند" إلا بقرار صريح موثَّق وقت تعريفه، لا افتراضًا متساهلًا.

`coverage_complete = true` **فقط** إذا كل بُعد `required=true` بلغ `authority_sufficient=true`
— **لا** لمجرد بلوغه حالة اسمها "ADMITTED" (كانت الصياغة القديمة تخلط B مع A ضمنيًا؛ التعريف
الجديد يمنع ذلك حرفيًا: Supporting وحده لا يكفي إطلاقًا لبُعد `requires_governing=true`، مهما
بلغت درجته أو عدد مرشحاته).

### آلة الحالة (لكل بُعد، مستقلة) — مُعدَّلة لتفصل الحاكم عن المساند

```
UNKNOWN
  → (الـBackbone يحدد البُعد كمطلوب لهذه المسألة) → SCOPED
SCOPED
  → (أي قناة استرجاع تجد مرشحًا أيًّا كان تصنيفه) → CANDIDATE_FOUND
  → (استُنفدت القنوات المُهيَّأة بلا أي نتيجة، §8) → DEAD_END
CANDIDATE_FOUND
  → (مرشح واحد على الأقل يبلغ شروط A، §4) → GOVERNING_VERIFIED
  → (لا A، لكن مرشح B موجود) → SUPPORTING_FOUND   # لا يُسمَّى ANCHORED أبدًا — B ليس مرساة
  → (لا A ولا B، C/D/U فقط) → يُصدِر CoverageRepairRequest، ثم DEAD_END إن فشلت المحاولة الوحيدة
GOVERNING_VERIFIED
  → (نجا فعليًا للسياق عبر §6) → ADMITTED_GOVERNING
  → (أُسقط رغم الترقية — ثغرة تصميم يجب ألا تحدث بعد §5/§6؛ إن حدثت تُسجَّل كخطأ حرج) → DEAD_END
SUPPORTING_FOUND
  → (نجا للسياق عبر المنافسة العادية) → ADMITTED_SUPPORTING
  → (لم ينجُ) → DEAD_END
```

**ملاحظة حاسمة:** الوصول لـ`ADMITTED_SUPPORTING` **لا يعني** `authority_sufficient=true` إلا
إذا كان `requires_governing=false` لهذا البُعد تحديدًا (التعريف أعلاه). هذا يمنع بالضبط ما رصده
المالك: وجود سند مساند لا يعني اكتمال البُعد إن كان يتطلب سندًا حاكمًا.

أي بُعد `required=true` عالق في `DEAD_END`، أو بلغ `ADMITTED_SUPPORTING` بينما
`requires_governing=true`، يُبقي `coverage_complete=false` ويُصدِر **Coverage Repair Request**
(إن لم يكن قد صدر بالفعل):

```
CoverageRepairRequest { dimension_id, attempted_channels: [...], reason }
```
يُرسَل لطبقة الاسترجاع لمحاولة **واحدة فقط** إضافية (استعلام موسَّع مستهدَف لهذا البُعد تحديدًا
— مثال: توسعة معجمية بمرادفات إضافية) — لا حلقة غير محدودة. فشلت المحاولة الثانية أيضًا؟
ينتقل البُعد لـ`DEAD_END` نهائيًا لهذا الطلب، ويُسجَّل في قائمة انتظار مراجعة Legal Dependency
Layer (§3) كمرشح فجوة تستحق قاعدة جديدة إن تكرر عبر طلبات مختلفة.

## 8. Search Exhaustion Contract
**(مُعدَّل 2026-09-14 — ثلاث حالات لا حالتان؛ "فُحصت كل القنوات" ≠ "غائب عن المتن")**

**تصحيح جوهري بأمر صريح:** `all configured channels attempted = true` **لا يعني إطلاقًا**
`authority absent from corpus` — دفتان مختلفتان كليًا: هل بحثنا بكل الطرق المُهيَّأة (Search
Exhaustion)، مقابل هل تحقَّقنا فعليًا وبشكل حاسم أن الكائن غير موجود في المتن أصلًا (Corpus
Absence). **ثلاث حالات مستقلة لا حالتان:**

```
search_manifest[dimension_id] = {
  deterministic_scope: bool, dense: bool, lexical: bool, explicit_citation: bool,
  chapter_gate: bool, xref: bool, legal_dependency_layer: bool,
  relevant_legislation_scope: bool,
  exhaustive_lookup_attempted: bool,   # جديد — انظر التمييز أدناه، منفصل عن القنوات الاحتمالية أعلاه
}
```

| الحالة | الشرط | ما يُسمح به مخرَجيًا |
|---|---|---|
| **`FOUND`** | مرشح واحد على الأقل ذو صلة عبر أي قناة | استشهاد عادي |
| **`NOT_FOUND_AFTER_CONFIGURED_SEARCH`** | كل القنوات الاحتمالية (`dense`/`lexical`/`bundle`/`chapter`/`xref`/الاستلزام) فُحصت بلا نتيجة، **لكن لا فحص حاسم شامل (exhaustive) أُجري** | **الحالة الافتراضية لأي غياب** — الصياغة الإلزامية: "لم يُعثر على نص مباشر ضمن نطاق البحث المتاح؛ يوصى بالتحقق المباشر" — **لا** "غير موجود" القاطعة |
| **`CORPUS_ABSENCE_VERIFIED`** | فحص حتمي شامل (لا احتمالي) أثبت الغياب — انظر الاختبار المطلوب لكل نوع سلطة أدناه | **الحالة الوحيدة** التي يجوز فيها تصريح قوي "غير موجود في المصادر" |

### الاختبار المطلوب للوصول لـ`CORPUS_ABSENCE_VERIFIED` بحسب نوع السلطة — لا يكفي Dense/LIKE أبدًا

**مبدأ عام:** `dense` top-K احتمالي (لا يضمن فحص كل نقطة)، و`lexical LIKE` عرضة لتفاوت الصياغة
والتطبيع — **لا يصلح أي منهما بمفرده دليلًا حاسمًا على الغياب**، مهما اتسع K أو تعدَّدت صياغات
LIKE. لكل نوع سلطة اختبار حتمي شامل فعليًا مختلف:

| نوع السلطة | الاختبار الحاسم (Exhaustive) | مثال تنفيذي |
|---|---|---|
| **مادة برقم محدَّد من قانون معروف** | استعلام مباشر شامل بمطابقة معرِّف/رقم مادة على القانون كله عبر PostgreSQL — لا بحث مرتَّب | `SELECT id FROM knowledge_objects WHERE id LIKE 'legis-X-%mN'` (فحص كل صفوف القانون، لا top-K) |
| **قانون/لائحة/مرسوم برقم وسنة** | مطابقة مباشرة على جرد التشريعات الحي المهيكَل (`legislation_inventory` القائمة فعلًا) — بنية مغلقة قابلة للحصر | تحقُّق وجود بادئة `legis-N-YYYY` في الجرد كاملًا |
| **مفهوم/آلية قانونية مفتوحة** (لا رقم مادة محدَّد، مثل "هل يوجد نص يعالج X؟") | **لا يوجد اختبار حاسم شامل ممكن فعليًا** — الفضاء المفاهيمي غير قابل للحصر بالكامل | **السقف الصادق هنا `NOT_FOUND_AFTER_CONFIGURED_SEARCH` دائمًا**، ولا يُدَّعى تجاوزه أبدًا — هذا اعتراف معماري صريح لا نقص تصميم |

**الأثر العملي المباشر:** غالبية الأسئلة القانونية الحقيقية (مفاهيمية لا مرقَّمة) **لن تبلغ
أبدًا** `CORPUS_ABSENCE_VERIFIED` — وهذا **مقصود ومطلوب**، لا عيبًا: يمنع النظام بنيويًا من
ادّعاء يقين لا يملكه، ويُبقي الصياغة المتحفظة هي الافتراضية دومًا لهذه الفئة الأوسع من الأسئلة.

## 9. أربعة مفاهيم منفصلة نهائيًا (لا "Recall" واحدة تغطيها)

| المفهوم | السؤال الذي يجيب عنه | المقياس المقترَح |
|---|---|---|
| **Search Coverage** | هل وجدنا المرشح في اتحاد المرشحين الخام؟ | `SearchCoverageRate` (ما كان يُسمى Candidate Recall) |
| **Legal Scope Coverage** | هل تعرَّف النظام أصلًا على كل الأبعاد القانونية المطلوبة؟ (مستقل عن العثور على مرشح) | `ScopeCompletenessRate` — نسبة الأبعاد التي بلغت `SCOPED` فأعلى من إجمالي الأبعاد المطلوبة فعليًا (يحتاج تعريفًا مرجعيًا مستقلًا للأبعاد "الحقيقية" لكل نوع مسألة، لا Gold Set IDs) |
| **Evidence Admission Coverage** | من المرساة الحاكمة المكتشَفة، كم بقي بعد القبول؟ | `AdmissionSurvivalRate` = عدد A/B الناجية ÷ عدد A/B المكتشَفة |
| **Context Coverage** | هل وصل الدليل المطلوب فعليًا لنص الطلب المُرسَل للنموذج؟ | `ContextDeliveryRate` — تحقُّق تجميع أخير (نادرًا ما يفشل بمعزل عن القبول، لكن يُقاس صراحة لسد أي فجوة تجميع لاحقة) |

## 10. القياس السلبي (Negative-Control Evaluation) — شرط قبل الثقة بـCoverage Checker

**المقياسان المطلوبان (تصميم، لا تنفيذ الآن):**
- **False No-Source Rate:** على أسئلة إيجابية (سند كافٍ موجود فعلًا)، كم مرة يُعلن النظام
  خطأً "غير موجود"؟
- **False Source-Sufficiency Rate:** على أسئلة سلبية (خارج النطاق/لا سند/سند جزئي فقط/نص قريب
  لفظيًا لكنه لا يحكم المسألة)، كم مرة يدَّعي النظام سندًا كافيًا خطأً؟

**آلية القياس المقترَحة:** حزمة تدقيق صغيرة مقيَّدة (10-20 نداء توليد حقيقي فعلي — **ليس**
قياسًا بلا توليد كباقي هذه المرحلة، بالضرورة، لأن هذين المقياسين لا يُقاسان إلا من **نص
الإجابة الفعلي**) على مجموعة منسَّقة تغطي الفئات الأربع المذكورة، بمراجعة بشرية أو حَكَم LLM
مستقل يُقيِّم دقة الإفصاح لكل إجابة. تُشغَّل **دوريًا لا مع كل التزام** (الكلفة أعلى من بقية
أدوات هذه المرحلة). **ملاحظة بعد حذف A4 (§4-مكرر):** لا مسار تصعيد اجتهادي نشط في هذا التصميم
أصلًا يحتاج بوابة تفعيل — فئة `U` لا تدخل الحجز ولا تصنع اكتفاءً بنفسها بأي حال. هذان المقياسان
يبقيان **شرطًا مسبقًا لأي مراجعة مستقبلية** لترقية `U` (المذكورة كاحتمال بعيد فقط في §4-مكرر)،
لا لأي سلوك مُفعَّل في هذا الإصدار من التصميم.

## 11. معالجة الانطباق الزمني (Temporal)

**لا يُعتبَر 6/6 نجاحًا معماريًا نهائيًا** (كما وثَّق القسم O من التقرير الأم) — عمود
`temporal_scope` فارغ 100% بنيويًا. التصميم المرحلي:

- **قصير المدى (بلا هجرة بيانات كبرى):** استعمال الإشارات المتفرقة القائمة فعلًا في
  `metadata` (`repealed_by`, `previous_versions`, `verification_status='superseded'`) —
  أي مرساة تحمل `verification_status=superseded` والسؤال ليس تاريخيًا صراحة → `temporal_status
  = resolved_superseded` **وجوبًا** يُقرَن ببديلها النافذ إن أمكن تحديده (نمط "قاعدة التحديث"
  القائم أصلًا في المشروع)، لا يُسقَط صامتًا.
- **حين لا توجد أي إشارة زمنية إطلاقًا لقانون قد يكون عُدِّل:** `temporal_status = unknown`
  صراحة — **لا افتراض** أن أعلى نتيجة استرجاعًا هي النافذة تلقائيًا. Coverage Checker يعكس
  هذا مباشرة (`temporal_status_known=false`) بدل الصمت.
- **بعيد المدى (خارج نطاق P2 هذا، يُذكَر للتوثيق فقط):** مشروع تعبئة `temporal_scope` فعليًا
  عبر القاعدة — لا يُصمَّم بعمق هنا، طبقًا لتوجيه "الحد الأدنى القابل للتطبيق الآن".

## 12. القياس عن بُعد (Telemetry) المطلوب

لكل طلب استوديو حي (إضافة بحتة لما هو موجود، بنفس نمط `draft_evidence`/`attrition` القائم):
- `deterministic_scope`: كل بُعد وقاعدته المطابِقة ومعرفاته الحاكمة.
- `haiku_axes_actual`: نص المحاور الفعلي (كما هو مسجَّل اليوم).
- `evidence_tiers`: تصنيف A/B/C/D لكل مرشح دخل `hits` مع `anchor_reason` إن وُجد.
- `admission_decisions`: قرار كل مرشح (`ADMIT_RESERVED`/`COMPETE_ON_BUDGET`/`DROP`) وسببه.
- `anchor_reservation_usage`: نسبة الحجز المستهلَك لكل نوع، وأي `overflow` مسجَّل.
- `coverage_checker_state`: حالة كل بُعد النهائية + `coverage_complete` + أي
  `CoverageRepairRequest` أُطلِق ونتيجته.
- `temporal_flags`: لكل مرساة، حالتها الزمنية.
- `search_exhaustion_manifest`: كما في §8، لكل بُعد.

**لوحات مجمَّعة مستقبلية (لا الآن):** `AdmissionSurvivalRate` عبر الزمن، `ScopeCompletenessRate`
بحسب الفرع القانوني، تكرار `CoverageRepairRequest` (مؤشر مباشر على فجوات تستحق قاعدة استلزام
جديدة في §3).

## 13. المخاطر

| الخطر | الوصف | التخفيف المصمَّم |
|---|---|---|
| **مراسٍ زائفة (False Anchors)** | قاعدة استلزام موسَّعة زيادة عن الحاجة تُرقّي مواد غير ذات صلة فعليًا | كتابة قواعد ضيقة إلزاميًا + بطارية انحدار على أسئلة محايدة (نفس نمط `_GATES` القائم) + حد أقصى مراسٍ لكل بُعد/قانون (§6) |
| **إغراق السياق (Context Flooding)** | تراكم مراسٍ من أبعاد متعددة يُضخِّم الحجز حتى يُزاحم الميزانية العادية | حد إجمالي أقصى للمراسي لكل طلب (فوق الحدود الفرعية في §6) |
| **توسّع مفرط (Over-Expansion)** | حلقة إصلاح تغطية غير محدودة، أو Legal Dependency Layer ينمو بلا ضبط | محاولة إصلاح واحدة فقط لكل بُعد (§7)؛ نمو الجدول القانوني حصرًا عبر بوابة اعتماد يدوية موثَّقة (§3) |
| **ثقة زائفة عبر تصعيد اجتهادي** | كانت مخاطرة A4 المحذوفة؛ الآن مُستبعَدة بنيويًا | `U` (§4-مكرر) لا تدخل الحجز ولا تصنع اكتفاءً بأي حال — لا حاجة لبوابة تفعيل لأنه لا سلوك مصعَّد أصلًا |
| **اعتماد زائف على نجاح ظاهري** | 15/15 بطارية أو Candidate Recall عالٍ يُقرَأ كدليل اكتمال (درس مسجَّل مسبقًا في التقرير الأم) | كل بوابة اعتماد أدناه (§14) تفحص الطبقة العميقة (Admission/Coverage) لا فقط الاسترجاع الأولي |

## 15. التوصية النهائية — أصغر تغيير إنتاجي أول

**التوصية: بناء P2.1 (Shadow Mode الكامل، الخطوة 1) — لا سلوك إنتاجي فيها إطلاقًا، لكنها ليست
"تليمتري وصفي فوق الخط القائم" كما اقتُرح سابقًا، بل تشغيل العمارة الجديدة بأكملها بمعزل تام.**

**السبب:** نفس المنهج الذي أثبت جدواه مرارًا في هذا المشروع (P0 وP1 معًا) — القياس قبل التغيير
— لكن بصرامة أعلى هذه المرة بأمر صريح: لا نكتفي بتسجيل تصنيفات وصفية فوق الخط الحالي (كما
اقترحت النسخة الأولى من هذا التصميم)، بل **نبني ونُشغِّل العمارة الجديدة بالكامل** في الظل،
فنحصل على مقارنة مباشرة (Current مقابل Shadow) بدل استنتاج غير مباشر من توزيعات وصفية. هذا
يكشف بدقة أكبر هل التصميم **يُصلح فعلًا** m166/m167/m30/تذبذب الاكتشاف **بلا** إسقاط أي سلطة
كانت تنجو أصلًا في الأساس — وهو معيار القرار الأهم (§10 من مستند P2.1) لا مجرد تحسّن متوسط.
التفاصيل الكاملة (المخطط، التليمتري، خطة الاختبار، تصميم fail-open) في مستند منفصل:
`docs/p2_1_shadow_mode_design.md`.

**لا تنفيذ لـP2.1 نفسه قبل مراجعتك للتصميم المفصَّل في المستند الجديد.**
